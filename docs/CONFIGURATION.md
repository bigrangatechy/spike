# Spike Configuration

## Purpose

This document specifies how all system configuration is generated, applied, and managed in Spike. It covers the `spike-config` tool — the configuration generator that writes all system files at install time and whenever a user changes a setting. This document exists to ensure that configuration is never ad-hoc, never hand-edited, and always traceable.

## Design Philosophy

**1. Configuration is code, not settings**

```
├── Config files are generated from templates + user choices
├── Users never edit config files (Golden Rule 1)
└── Every config file has a comment: "Generated by spike-config"
```

**2. Single source of truth**

```
├── Settings GUI writes to a single state store
├── spike-config reads state store and generates config files
└── Config files are derived artifacts, not primary data
```

**3. Idempotent generation**

```
├── Running spike-config twice produces the same output
├── No accumulation of duplicate entries or stale settings
└── If a config file is deleted: spike-config regenerates it
```

**4. Traceable changes**

```
├── Every config change logged with timestamp + reason
├── State store contains full history of changes
└── Recovery from bad config: restore previous state
```

## spike-config Architecture

### Overview

`spike-config` is the configuration engine for Spike. It is **NOT** a daemon — it runs on-demand (invoked by Settings GUI or by systemd triggers).

```
┌──────────────────────────────────────────────────┐
│              Settings GUI                         │
│  (User changes a setting, e.g., swappiness)      │
└──────────┬───────────────────────────────────────┘
           │ DBus call
           ▼
┌──────────────────────────────────────────────────┐
│              spike-config                         │
│  1. Reads current state store                    │
│  2. Applies change to state store                │
│  3. Regenerates affected config files             │
│  4. Restarts/reloads affected services            │
│  5. Logs the change                              │
└──────────┬───────────────────────────────────────┘
           │
    ┌──────┴───────┬────────────┬───────────────┐
    ▼              ▼            ▼               ▼
┌─────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐
│ State   │ │ Config   │ │ Service  │ │ Change Log   │
│ Store   │ │ Files   │ │ Reload   │ │              │
│         │ │ (/etc/)  │ │          │ │              │
└─────────┘ └──────────┘ └──────────┘ └──────────────┘
```

### Change Log

Every configuration change is logged.

- **Location:** `/var/lib/spike/config/changelog.json` 

- **Format:** JSON array (append-only) 

- **Permissions:** `644` (`root:root`) 

- **Retention:** Unlimited (full history preserved) 

- **Maximum entries:** 5000 (oldest pruned beyond this) 

**Structure:**

  {

## Config File Generation

### Templates

`spike-config` uses template files to generate system configuration. Templates contain variables that are substituted with values from the state store.

- **Template location:** `/usr/lib/spike/config/templates/` 

- Each template is a static file with `{{variable}}` placeholders. 

**Template: `sysctl-memory.tpl`**

```
# Spike Memory Configuration
# Generated by spike-config at {{timestamp}}
# DO NOT EDIT — Use Settings → Advanced → Memory to change
# Changelog reference: {{changelog_id}}
# Swappiness (lower = prefer RAM, higher = prefer swap)
vm.swappiness = {{swappiness}}
# VFS cache pressure
vm.vfs_cache_pressure = {{vfs_cache_pressure}}
# Transparent hugepages (controlled by kernel param, but set here too)
# (transparent_hugepage=madvise on kernel command line)
```

**Template: `grub-default.tpl`**

```
# Spike GRUB2 Configuration
# Generated by spike-config at {{timestamp}}
# DO NOT EDIT — Use Settings → Advanced → Boot to change
GRUB_TIMEOUT={{grub_timeout}}
GRUB_TIMEOUT_STYLE={{grub_timeout_style}}
GRUB_DEFAULT=0
GRUB_DISABLE_RECOVERY=false
GRUB_THEME=/boot/grub/themes/spike/theme.txt
GRUB_GFXMODE=auto
GRUB_GFXPAYLOAD_LINUX=keep
GRUB_BACKGROUND=/boot/grub/themes/spike/background.png
GRUB_CMDLINE_LINUX_DEFAULT="{{boot_parameters_joined}}"
GRUB_CMDLINE_LINUX=""
GRUB_DISABLE_OS_PROBER=true
GRUB_TERMINAL_OUTPUT=gfxterm
GRUB_FONT=/boot/grub/themes/spike/pf2/font.pf2
GRUB_DISABLE_SUBMENU=y
```

**Template: `pipewire-conf.tpl`**

```
# Spike PipeWire Configuration
# Generated by spike-config at {{timestamp}}
# DO NOT EDIT — Use Settings → Sound to change
[context]
log.level = 1
log.timestamp = false
log.color = false
[properties]
default.clock.rate = {{sample_rate}}
default.clock.quantum = 1024
default.clock.min-quantum = 32
default.clock.max-quantum = 2048
default.clock.allowed-rates = [ {{sample_rate}} ]
```

**Template: `networkmanager-conf.tpl`**

```
# Spike NetworkManager Configuration
# Generated by spike-config at {{timestamp}}
# DO NOT EDIT — Use Settings → Network to change
[main]
dhcp = {{dhcp_client}}
dns = {{dns_resolver}}
plugins = keyfile
[connection]
ipv6.method = auto
ipv6.ip6-privacy = 2
autoconnect = true
wifi.cloned-mac-address = preserve
[wifi]
scan-rand-mac-address = no
```

### Generation Process

When `spike-config` regenerates a config file:

1. Read state store (`/var/lib/spike/config/state.json`) 

2. Select template based on module and setting 

3. Substitute variables: 

   - a. Replace `{{variable}}` with value from state store 

   - b. Replace `{{timestamp}}` with current UTC timestamp 

   - c. Replace `{{changelog_id}}` with current changelog entry ID 

4. Validate generated file: 

   - a. Syntax check (INI format, shell syntax, JSON validity) 

   - b. Verify all variables substituted (no leftover `{{}}`) 

   - c. Verify no empty critical fields 

5. Write to temporary file (same directory + `.tmp` extension) 

6. `fsync(temporary file)` 

7. Rename to target path (atomic replace) 

8. `fsync(directory)` 

9. Log to `changelog.json` 

10. Reload affected service (if needed) 

11. Emit DBus signal (notify Settings GUI that config changed) 

If any step fails:

```
├── Temporary file cleaned up
└── Original config file remains unchanged (atomic write guarantees this)
```

### Idempotency

`spike-config` is fully idempotent:

```
├── Running spike-config --generate-all produces identical output
│   every time (given same state store)
├── No duplicate entries accumulate
├── No stale settings persist
├── spike-config can be safely run multiple times
├── If a config file is missing: regenerated
├── If a config file is corrupted: regenerated
├── If a config file was hand-edited: overwritten with correct version
└── If state store is missing: regenerated from hardware detection + defaults
```

## Module Specifications

### Memory Module

**Config files generated:**

```
├── /etc/sysctl.d/99-spike-memory.conf        → swappiness, vfs_cache_pressure
├── /etc/systemd/zram-generator.conf           → ZRAM device parameters
├── /etc/udev/rules.d/99-spike-zram.rules     → ZRAM udev trigger
└── /etc/default/earlyoom                       → earlyoom configuration
```

**Template variables (from state store):**

```
├── {{swappiness}}                              → 15 (SSD), 5 (HDD), 10 (SD/USB)
├── {{vfs_cache_pressure}}                     → 100 (default)
├── {{zram_size_mb}}                            → min(RAM, 4096) Standard, min(RAM, ∞) Plus
├── {{zram_compression}}                        → zstd
├── {{zram_priority}}                          → 100
├── {{swap_file_path}}                          → /swapfile
├── {{swap_file_size_mb}}                       → 8192 (SSD/HDD), 4096 (SD/USB)
├── {{earlyoom_threshold}}                      → 10 (% of memory+swap)
├── {{earlyoom_protected}}                      → comma-separated list
└── {{earlyoom_prefer}}                         → comma-separated list
```

**Service reloads after generation:**

```
├── sysctl --system (reload sysctl)
├── systemctl restart earlyoom (if config changed)
└── (ZRAM changes require reboot — user notified)
```

### Boot Module

**Config files generated:**

```
├── /etc/default/grub                           → GRUB parameters and behavior
├── /boot/.spike/boot-count                    → Boot failure counter
└── (Plymouth theme selection: plymouth-set-default-theme)
```

**Template variables:**

```
├── {{grub_timeout}}                            → 0 (hidden)
├── {{grub_timeout_style}}                     → hidden
├── {{esc_window_seconds}}                     → 3 (configurable 1–10)
├── {{boot_parameters_joined}}                  → "quiet splash zswap.enabled=0 transparent_hugepage=madvise"
└── {{plymouth_theme}}                          → spike-minimal (Standard) / spike-full (Plus)

**Post-generation actions:**

```
├── update-grub (regenerate grub.cfg)
└── update-initramfs -u (if Plymouth theme changed)
```

**Service reloads:**

```
└── None (GRUB changes take effect on next boot)

**Boot failure counter manipulation:**

```
├── spike-config --boot-count get             → Returns current count
├── spike-config --boot-count reset           → Writes 0 to file
├── spike-config --boot-count increment       → Adds 1 to file
├── Settings → Advanced → Boot → [Reset counter]
└── Normally managed automatically by initramfs + spike-session
```

## Hardware Detection (spike-config --detect)

`spike-config --detect` runs hardware detection modules and updates the state store with detected hardware information.

This runs:

```
├── At install time (after base system is installed)
├── On first boot (verifies detection was correct)
└── Manually via Settings → Advanced → Diagnostics → [Re-detect hardware]
```

**Detection modules (from `spike-installer/detect/`):**

```
├── cpu.cpp        → CPU model, cores, bogomips, classification
├── storage.cpp    → Storage type, size, rotational flag, eMMC/USB check
├── gpu.cpp        → GPU vendor, model, driver, VA-API driver
├── network.cpp    → Wi-Fi/Ethernet adapter, driver module
├── bluetooth.cpp  → Bluetooth adapter presence
└── modem.cpp      → Mobile broadband modem presence
```

**Detection output updates state store:**

```
{
  "hardware": {
    "cpu": { ... },
    "ram": { ... },
    "gpu": { ... },
    "storage": { ... },
    "network": { ... }
  }
}
```

After detection, `spike-config` regenerates **ALL** config files to ensure they match the detected hardware (in case hardware changed, e.g., storage upgrade, RAM upgrade, or USB Wi-Fi adapter added).

**If hardware changes are detected:**

```
├── Notification: "Spike detected hardware changes: [list].
│   System configuration has been updated."
├── Relevant config files regenerated
├── User may need to reboot for all changes to take effect
└── Changelog records all regenerated files
```

## CLI Interface

`spike-config` is primarily invoked by the Settings GUI via DBus. However, a CLI interface exists for developers and power users.

**Usage:**

```
├── spike-config --generate-all              → Regenerate all config files
├── spike-config --generate <module>         → Regenerate one module's files
├── spike-config --detect                    → Run hardware detection
├── spike-config --state                     → Dump state store to stdout
├── spike-config --state-get <module> <key>  → Get specific value
├── spike-config --state-set <module> <key> <value> → Set specific value
├── spike-config --changelog                 → Show recent config changes
├── spike-config --rollback <entry-id>       → Roll back a specific change
└── spike-config --validate                  → Validate all config files
```

> **CRITICAL: The CLI is for DEVELOPERS ONLY.**

> - The CLI is documented in the dev guide, NOT the user guide 

> - Normal users use the Settings GUI (Golden Rule 1 and 2) 

> - The CLI exists for debugging, scripting, and automated testing 

> - The CLI is not hidden — it's available but not advertised 

**Example developer usage:**

```
spike-config --generate memory
→ Regenerates /etc/sysctl.d/99-spike-memory.conf, zram-generator.conf,
  zram udev rule, earlyoom config
→ Does not affect other modules
→ Logs to changelog.json
```

**Rollback example:**

```
spike-config --rollback <changelog-entry-id>
→ Reads changelog entry
→ Reverts state store value to old_value
→ Regenerates affected config files
→ Logs rollback action in changelog
→ Reloads affected services
```

## State Store Recovery

If the state store (`/var/lib/spike/config/state.json`) is lost or corrupted:

**Recovery process:**

1. `spike-config` detects invalid/missing state store at startup 

2. Runs hardware detection (`spike-config --detect`) 

3. Generates new state store with: 

   - **Hardware:** from detection results 

   - **Defaults:** from `/usr/lib/spike/config/defaults.json` 

   - **Variant:** detected from installed packages (`spike-standard` or `spike-plus-meta`) 

4. Regenerates ALL config files based on new state store 

5. Notifies user: *"Spike's configuration was lost and has been regenerated. Your settings have been reset to defaults. Please review your settings in Settings."* 

6. User can re-customize as needed 

**`defaults.json`:**

```
├── Location: /usr/lib/spike/config/defaults.json
├── Contains default values for every configuration option
├── Different defaults for Standard vs Plus variant
└── Used as fallback when state store is unavailable
```

This ensures the system is **always** configurable, even if the state store is lost. There is no "unrecoverable config" state.

## Atomic Write Guarantee

All config file writes are atomic.

**Process:**

1. Generate config content to string 

2. Write content to temporary file (target path + `.spike-tmp`) 

3. `fsync(temporary file)` — ensures data is on disk 

4. `rename(temporary file, target path)` — atomic replace 

5. `fsync(target directory)` — ensures rename is committed 

**Guarantee:**

```
├── Config file is either the OLD version or the NEW version
├── Never a partially-written or corrupted file
├── If power loss occurs during write:
│   ├── If before step 4: old config intact, new config lost
│   └── If after step 4: new config intact
└── This is the same guarantee as the notification daemon's history writes
```

**Why this matters:**

```
├── Power failure during config write doesn't break the system
├── Disk full condition: write fails cleanly (no partial file)
├── Process killed mid-write: old config remains
└── User confidence: "Changing a setting won't break my system"
```

## Settings GUI Integration

The Settings GUI communicates with `spike-config` via DBus.

**DBus interface:** `org.spike.Config`

**Methods:**

```
├── GetState() → JSON string (full state store)
├── GetModuleState(string module) → JSON string (one module's state)
├── SetSetting(string module, string key, variant value) → bool success
├── GenerateAll() → bool success
├── GenerateModule(string module) → bool success
├── DetectHardware() → JSON string (detection results)
├── GetChangelog(int count) → JSON string (recent changes)
├── Rollback(string entry_id) → bool success
└── ValidateAll() → bool success
```

**Signals:**

```
├── StateChanged(string module, string key, variant old_value, variant new_value)
└── ConfigRegenerated(string module, array[string] files)
```

**The Settings GUI:**

```
├── Calls GetState() when a settings page is opened
├── Calls SetSetting() when user changes a setting
├── Listens for StateChanged signal to update other open pages
├── Listens for ConfigRegenerated to show "Settings applied" feedback
└── Never writes config files directly — always goes through spike-config
```

**This separation ensures:**

```
├── Settings GUI is a thin client (doesn't know about file paths or templates)
├── spike-config is the single writer of config files
├── Multiple settings pages can be open without conflict
└── CLI and GUI produce identical results
```
