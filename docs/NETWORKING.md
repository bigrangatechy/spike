# Spike Networking

## Purpose

This document specifies all networking configuration in Spike — Wi-Fi, Ethernet, DNS, firewall, Bluetooth, VPN, and mobile broadband. Networking is critical because a laptop without internet is a laptop nobody wants. On target hardware, getting Wi-Fi working is often the single hardest part of reviving an old machine.

## Design Principles

**1. All firmware on the ISO**

```
`├── User never downloads firmware post-install`

`└── Wi-Fi works on first boot, guaranteed (if hardware is functional)`
```

**2. NetworkManager is the single network manager**

```
`├── No systemd-networkd, no netctl, no wicd`

`└── One configuration source, one GUI, one DBus interface`
```

**3. Firewall on by default**

```
`├── Deny all incoming connections`

`├── Allow all outgoing connections`

`└── User can open ports via GUI (Golden Rule 1)`
```

**4. No network services exposed**

```
`├── No SSH server (not installed)`

`├── No file sharing server (not installed)`

`├── No web server (not installed)`

`└── The laptop is a client, not a server`
```

## NetworkManager

### Configuration

NetworkManager is the sole network manager. No alternatives installed.

Main config: `/etc/NetworkManager/NetworkManager.conf`

Spike customizations (applied by `spike-config`):

```
*`\# Spike NetworkManager Configuration`*

*`\# Generated by spike-config at install time`*


`\[main\]`

*`\# Use dhclient for DHCP (more reliable on old routers than internal)`*

`dhcp = dhclient`


*`\# DNS resolution via systemd-resolved`*

`dns = systemd-resolved`


*`\# Plugins: ifupdown is disabled (no /etc/network/interfaces management)`*

`plugins = keyfile`


*`\# Default IPv4 privacy extensions`*

`\[connection\]`

*`\# Prefer IPv4 over IPv6 (more stable on consumer routers)`*

`ipv6.method = auto`

*`\# Enable IPv6 privacy extensions (RFC 4941)`*

`ipv6.ip6-privacy = 2`


*`\# Wi-Fi behavior`*

`\[wifi\]`

*`\# Scan for networks actively (passive scanning is slower)`*

`scan-rand-mac-address = no`

*`\# Allow Wi-Fi power saving (controlled by power profile — see POWER-MANAGEMENT.md)`*


*`\# Connection defaults`*

`\[connection\]`

*`\# Auto-connect to saved networks`*

`autoconnect = true`

*`\# Don't share connection profiles between users`*

`permissions =`

*`\# Stable MAC address (don't randomize — confuses some routers)`*

`wifi.cloned-mac-address = preserve`
```

### Keyfile Storage

NetworkManager stores connection profiles as keyfiles:

Location: `/etc/NetworkManager/system-connections/`

Each Wi-Fi network is a separate file:

```
`├── \[SSID\].nmconnection`

`├── Contains: SSID, password (encrypted), security type, IPv4/v6 method`

`├── Permissions: 600 (root only — passwords protected)`

`└── Backed up during Spike Rescue (if user data backup includes /etc)`
```

Example file structure:

```
`\[connection\]`

`id=Home WiFi`

`uuid=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`

`type=wifi`

`autoconnect=true`


`\[wifi\]`

`ssid=Home WiFi`

`mode=infrastructure`

`mac-address=XX:XX:XX:XX:XX:XX`


`\[wifi-security\]`

`key-mgmt=wpa-psk`

`psk=\*\*\*\*\*\*\*\*`


`\[ipv4\]`

`method=auto`


`\[ipv6\]`

`method=auto`
```

### DHCP Behavior

DHCP client: `dhclient` (not NetworkManager internal)

Why dhclient:

```
`├── More compatible with older consumer routers`

`├── Better at renewing leases on flaky networks`

`├── Handles DHCP fallback (APIPA 169.254.x.x) gracefully`

`└── Familiar to support staff for debugging`
```

DHCP timeout: 45 seconds (default)

```
`├── If DHCP fails: NetworkManager shows "No IP address"`

`├── User can configure static IP via Settings → Network`

`└── Automatic fallback to APIPA (link-local) address`
```

Static IP configuration:

```
`├── Available in Settings → Network → \[Connection\] → IPv4`

`├── Method: Automatic (DHCP) or Manual (Static)`

`├── If Manual: IP address, netmask, gateway, DNS fields`

`└── Stored in keyfile, applied by NetworkManager`
```

### DNS Resolution

DNS resolver: `systemd-resolved`

Why systemd-resolved:

```
`├── Integrated with systemd (no extra dependency)`

`├── Caches DNS queries (faster lookups)`

`├── Handles DNS-over-TLS (optional, future)`

`├── Manages /etc/resolv.conf symlink`

`└── DBus interface for status reporting`
```

Configuration: `/etc/systemd/resolved.conf`

```
`\[Resolve\]`

*`\# Use router-provided DNS by default`*

`DNS=`

*`\# Fallback DNS (if router doesn't provide any)`*

`FallbackDNS=1.1.1.1 8.8.8.8`

*`\# Enable DNS-over-TLS (off by default — some routers break it)`*

`DNSOverTLS=no`

*`\# Cache`*

`Cache=yes`

*`\# DNSSEC (validation)`*

`DNSSEC=no`
```

`/etc/resolv.conf` is a symlink:

```
`└── /etc/resolv.conf → /run/systemd/resolve/stub-resolv.conf`
```

**Settings → Network** shows:

```
`├── Current DNS servers (from DHCP or static config)`

`├── DNS server response time (diagnostic)`

`└── Option to override DNS (Settings → Network → Advanced → DNS)`
```

## Wi-Fi

### Firmware

**ALL Wi-Fi firmware is pre-installed on the ISO.** No post-install firmware download is required. This is critical for the target scenario: a user reviving an old laptop may not have Ethernet available, so Wi-Fi must work immediately.

Firmware packages included on ISO:

```
`├── linux-firmware              → Intel (iwlwifi), Atheros (ath), Realtek (rtl)`

`├── bcmwl-kernel-source         → Broadcom (proprietary)`

`├── firmware-atheros            → Older Atheros devices`

`├── firmware-realtek            → Realtek chips (some require this)`

`└── firmware-misc-nonfree       → Miscellaneous firmware blobs`
```

Driver modules and their firmware:

#### Intel Wi-Fi

Module: `iwlwifi` Firmware location: `/lib/firmware/intel/`

Supported chips:

```
`├── Intel Wireless-AC 9560 (Celeron N4020 onboard Wi-Fi)`

`├── Intel Wireless-AC 9260, 9270`

`├── Intel Dual Band Wireless-AC 3160, 3165, 3168`

`├── Intel Dual Band Wireless-AC 7260, 7265`

`├── Intel Wireless-N 1000, 1030, 1300`

`├── Intel Centrino Advanced-N 6235, 6200, 6205`

`├── Intel Pro/Wireless 2100, 2200BG (very old, may not work)`

`└── All newer Intel wireless chipsets`
```

Firmware loading:

```
`├── iwlwifi module loads automatically at boot (udev-triggered)`

`├── Firmware blob loaded from /lib/firmware/intel/`

`├── If firmware missing: dmesg shows "firmware: failed to load"`

`└── On Spike: firmware is always present (ISO includes all)`
```

Module parameters (Spike default):

```
`├── 11n\_disable=0  (enable 802.11n — fastest)`

`├── power\_save=1   (enable power saving — controlled by power profile)`

`├── swcrypto=0     (hardware crypto offload)`

`└── These are set in /etc/modprobe.d/spike-iwlwifi.conf`
```

#### Atheros Wi-Fi

Modules: `ath9k`, `ath9k\_htc`, `ath10k`, `ath10k\_pci`, `ath11k` Firmware location: `/lib/firmware/ath9k\_hw/`, `/lib/firmware/ath10k/`

Supported chips:

```
`├── Atheros AR9285, AR9287 (single-band Wireless-N)`

`├── Atheros AR9462, AR9485 (Wireless-N)`

`├── Qualcomm Atheros QCA9377, QCA6174 (Wireless-AC)`

`├── Qualcomm Atheros QCA6390 (Wi-Fi 6)`

`├── TP-Link USB adapters (ath9k\_htc)`

`└── Various USB Wi-Fi dongles`
```

Module parameters: None custom (defaults are fine) Firmware loading: Automatic via udev

Known issues:

```
`├── ath10k sometimes fails firmware load on first boot`

`│   └── Fix: modprobe -r ath10k\_pci && modprobe ath10k\_pci (handled automatically)`

`└── Spike handles this via a udev rule that retries firmware load`
```

#### Realtek Wi-Fi

Modules: `rtl8723de`, `rtl8188ee`, `rtl8192ce`, `rtl8821ce`, `rtl8822bu`, `rtl88x2bu` Firmware location: `/lib/firmware/rtlwifi/`, `/lib/firmware/rtl\_bt/`

Supported chips:

```
`├── RTL8723DE (common in budget laptops — Celeron N4020 boards)`

`├── RTL8188CE, RTL8192CE, RTL8192EE`

`├── RTL8821CE, RTL8822BE`

`├── RTL8812AU, RTL8822BU (USB dongles)`

`├── RTL88x2BU (USB Wi-Fi 6 dongles)`

`└── Various generic USB Wi-Fi adapters`
```

Module parameters (RTL8723DE):

```
`├── ant\_sel=2     (antenna selection — improves signal on some laptops)`

`├── power\_mgn=1   (power management)`

`└── Set in /etc/modprobe.d/spike-rtl8723de.conf`
```

Known issues:

```
`├── RTL8723DE historically had weak signal until ant\_sel=2`

`├── Some RTL8812AU USB dongles require dkms-rtl8812au package`

`│   └── Included on ISO as DKMS module (builds during install)`

`├── RTL8822BU may require dkms-rtl8822bu package`

`│   └── Included on ISO as DKMS module`

`└── Spike includes all known Realtek DKMS drivers on ISO`
```

#### Broadcom Wi-Fi

Module: `wl` (proprietary, via `bcmwl-kernel-source`) Firmware: Proprietary blob included in package

Supported chips:

```
`├── BCM4313, BCM43142, BCM43143 (Wireless-N)`

`├── BCM43428, BCM4360 (Wireless-AC)`

`├── BCM4350, BCM4356 (Wireless-AC)`

`├── BCM43455 (Raspberry Pi onboard — not relevant here but supported)`

`└── Various MacBook/Air Wi-Fi chips`
```

Installation:

```
`├── bcmwl-kernel-source builds a DKMS module`

`├── Requires kernel headers (installed as dependency)`

`├── If Secure Boot is enabled: MOK (Machine Owner Key) enrollment required`

`│   ├── User prompted at install time: "Broadcom Wi-Fi requires`

`│   │   Secure Boot enrollment. You will be prompted to enroll a key`

`│   │   on the next reboot."`

`│   ├── On next reboot: MOK enrollment screen (blue screen, text)`

`│   │   ├── User selects "Enroll MOK"`

`│   │   ├── Enters password set during install`

`│   │   └── Module loads on subsequent boots`

`│   └── If user misses enrollment: module fails to load, Wi-Fi doesn't work`

`│       └── Fix: Re-run spike-config --broadcom (via Settings diagnostic)`

`└── If Secure Boot is disabled: module loads normally`
```

Module parameters: None custom

Conflict with other drivers:

```
`├── bcmwl conflicts with b43 and ssb modules`

`├── spike-config blacklists b43 and ssb if Broadcom detected`

`└── /etc/modprobe.d/spike-broadband-blacklist.conf:`

`    blacklist b43`

`    blacklist ssb`

`    blacklist bcma`

`    blacklist brcmsmac`
```

### Wi-Fi Power Management

Wi-Fi power saving is controlled by the power profile, not by a static configuration. See `POWER-MANAGEMENT.md` for full details.

Implementation:

```
`├── NetworkManager's wifi.powersave property:`

`│   ├── 0 (default): Don't touch (leave to driver default)`

`│   ├── 1: Disable power saving`

`│   ├── 2: Enable power saving`

`│   └── 3 (default NM behavior): Enable power saving`

`├── Spike sets this dynamically:`

`│   ├── Performance profile (AC): wifi.powersave = 1 (off)`

`│   ├── Battery Saver profile: wifi.powersave = 2 (on)`

`│   └── Changed by spike-config-power-service (responds to AC events)`

`└── Changes apply immediately (no disconnection needed)`
```

`iwconfig`-level power saving:

```
`├── Some older drivers respond better to iwconfig power management`

`├── Spike applies iwconfig power setting as fallback`

`└── Done via udev rule (not ideal, but functional)`
```

**Settings → Power → Advanced:**

```
`├── Wi-Fi power saving: \[Adaptive\] ▼`

`│   ├── Off (best performance)`

`│   ├── On (best battery)`

`│   └── Adaptive (follow power profile)`

`└── Changes apply to current connection immediately`
```

### Roaming and Aggressiveness

Wi-Fi roaming aggressiveness (bgscan):

```
`├── NetworkManager default bgscan: every 60 seconds`

`├── Spike leaves this at default`

`├── More aggressive scanning: faster roaming but more battery drain`

`├── Less aggressive: slower roaming but saves power`

`└── Not exposed to user (too technical, defaults are fine)`
```

## Ethernet

### Wired Connections

Most Celeron-era laptops have an Ethernet port. Spike supports Ethernet out of the box with no configuration required.

Driver modules:

```
`├── Realtek: r8169 (most common onboard Ethernet)`

`├── Intel: e1000e (ThinkPad, business laptops)`

`├── Broadcom: tg3, bnx2 (some HP/Dell laptops)`

`├── Atheros: atl1c, atl1e (some budget laptops)`

`└── USB-Ethernet adapters: asix, cdc\_ether, r8152`
```

Configuration:

```
`├── NetworkManager auto-detects Ethernet port`

`├── Auto-connects when cable plugged in`

`├── DHCP by default`

`├── If no DHCP: APIPA fallback (169.254.x.x, link-local)`

`└── User can configure static IP in Settings → Network`
```

**Settings → Network → Wired:**

```
`├── Status: Connected / Disconnected`

`├── Speed: 1000 Mbps / 100 Mbps / 10 Mbps`

`├── IP Address: 192.168.1.42 (from DHCP)`

`├── Gateway: 192.168.1.1`

`├── DNS: 192.168.1.1, 1.1.1.1`

`└── \[Configure\] → IPv4/IPv6, static IP, DNS override`
```

Link negotiation:

```
`├── Auto-negotiation enabled by default`

`├── If auto-neg fails: forced to 100 Mbps half-duplex (fallback)`

`├── ethtool used internally by NetworkManager for link config`

`└── User never needs to run ethtool manually`
```

## Firewall (ufw)

### Configuration

Firewall: `ufw` (Uncomplicated Firewall) — frontend to nftables/iptables

State: **ENABLED** at install time, always on

Default rules:

```
`├── Default incoming: DENY`

`├── Default outgoing: ALLOW`

`├── Default forward: DENY`

`├── Default routed: DENY`

`└── No port-specific rules (everything incoming is blocked)`
```

Command-line equivalent (applied by `spike-config`):

```
`ufw default deny incoming`

`ufw default allow outgoing`

`ufw default deny forward`

`ufw --force enable`
```

Configuration files:

```
`├── /etc/ufw/ufw.conf              → Main config (ENABLED=yes)`

`├── /etc/ufw/user.rules            → User-defined rules`

`├── /etc/default/ufw               → Default policies`

`└── /lib/ufw/user.rules            → System default rules (don't modify)`
```

### What The Firewall Blocks

By default, **ALL** incoming connections are blocked. This means:

**Blocked:**

```
`├── Remote SSH access (ssh is not installed anyway)`

`├── File sharing (Samba, NFS not installed)`

`├── Screen sharing (VNC not installed)`

`├── Remote desktop (RDP not installed)`

`├── Printer discovery (mDNS — see below)`

`├── Network scanners finding the laptop`

`└── Any application listening on a port`
```

**Allowed:**

```
`├── Outgoing HTTP/HTTPS (web browsing)`

`├── Outgoing DNS queries`

`├── Outgoing email (IMAP/SMTP)`

`├── Outbound VPN connections`

`├── Outgoing game connections`

`└── Return traffic for established connections (conntrack)`
```

### Printer Discovery Exception

mDNS (multicast DNS) is used for printer discovery.

By default, ufw blocks multicast traffic. This means:

```
`├── Network printers may not be discovered automatically`

`├── avahi-daemon is installed (for printer discovery)`

`└── User can allow mDNS via Settings → Advanced → Firewall → \[Add rule\]`
```

Spike adds an avahi-specific rule at install time:

```
`ufw allow 5353/udp`
```

This allows:

```
`├── Printer discovery via Bonjour/mDNS`

`├── Chromecast discovery`

`├── AirPrint discovery`

`└── Other local network service discovery`
```

The rule is pre-configured and visible in the firewall rules list. User can delete it if they don't want printer discovery.

## Bluetooth

### Conditional Activation

Bluetooth is **not** always running. It is activated conditionally:

Detection at boot:

```
`├── spike-session checks for Bluetooth adapter (hciconfig or rfkill)`

`├── If adapter present: BlueZ daemon starts, applet loads`

`├── If adapter absent: BlueZ daemon does NOT start, applet not loaded`

`└── If USB Bluetooth dongle inserted later: udev triggers BlueZ start + applet load`
```

This saves memory and power on devices without Bluetooth hardware. A Celeron N4020 laptop may or may not have Bluetooth — detection handles both.

Implementation:

```
`├── /etc/udev/rules.d/99-spike-bluetooth.rules:`

`│   \# Trigger Spike Bluetooth startup when adapter appears`

`│   ACTION=="add", SUBSYSTEM=="bluetooth", RUN+="/usr/lib/spike/spike-bt-start"`

`│   \# If adapter removed, stop BlueZ (after grace period)`

`│   ACTION=="remove", SUBSYSTEM=="bluetooth", RUN+="/usr/lib/spike/spike-bt-stop"`

`├── spike-bt-start:`

`│   ├── systemctl start bluetooth`

`│   ├── DBus signal to spike-panel to load Bluetooth applet`

`│   └── Notification: "Bluetooth adapter detected. Click the Bluetooth`

`│       icon to pair devices."`

`└── spike-bt-stop:`

`    ├── Wait 30 seconds (in case of brief disconnect)`

`    ├── If no adapter present: systemctl stop bluetooth`

`    └── DBus signal to remove Bluetooth applet from panel`
```

### BlueZ Configuration

Bluetooth daemon: `bluetoothd` (BlueZ) Config: `/etc/bluetooth/main.conf`

Spike customizations:

```
`\[General\]`

*`\# Device class: Laptop`*

`Class = 0x00020c`

*`\# Discoverable timeout (seconds) — 0 means never auto-disable`*

`DiscoverableTimeout = 0`

*`\# Timeout for adapter to stay discoverable when pairing`*

`PairableTimeout = 60`

*`\# Adapter will be powered on when daemon starts`*

`AutoEnable = true`

*`\# Always allow incoming pairing (for pairing from phone)`*

`Privacy = off`

*`\# Controller mode: dual (BR/EDR + LE)`*

`ControllerMode = dual`

*`\# Fast connectable (reduce latency for audio)`*

`FastConnectable = true`

*`\# Experimental features (LE Audio support)`*

`Experimental = true`


`\[Policy\]`

*`\# Auto-connect to last device on adapter power-on`*

`AutoEnable = true`
```

### Bluetooth Audio

Bluetooth audio is handled by PipeWire (not a separate PulseAudio module).

See `MULTIMEDIA.md` for codec details (SBC, AAC, LDAC, aptX).

Bluetooth audio flow:

```
`├── Device paired via Bluetooth applet (pairing wizard)`

`├── Audio profile selected by WirePlumber:`

`│   ├── A2DP (high-quality audio output, no mic)`

`│   └── HSP/HFP (lower quality, includes mic for calls)`

`├── PipeWire routes audio to Bluetooth device`

`└── Volume controlled via Volume applet (same as wired speakers)`
```

Known issues:

```
`├── Some older Bluetooth headsets have pairing issues with BlueZ 5`

`├── LE Audio devices may require experimental mode (enabled above)`

`├── Bluetooth audio latency: 100-300ms (fine for music, noticeable for video)`

`└── Workaround: Use wired headphones for gaming/video sync`
```

### Bluetooth File Transfer

Spike supports Bluetooth file transfer (OBEX):

Package: `bluez-obexd` (installed by default)

```
`├── Receives files sent from other Bluetooth devices`

`├── Incoming files saved to ~/Downloads/Bluetooth/`

`├── Notification: "Incoming file: \[filename\] from \[device\]. Accept?"`

`├── Accept/Reject dialog before file is saved`

`└── No terminal commands needed`
```

Sending files:

```
`├── Right-click file in Dolphin → "Send via Bluetooth"`

`├── Select target device from paired devices`

`├── Progress shown in notification`

`└── Completion notification on success/failure`
```

```
`├── Packages: network-manager-openvpn, network-manager-openvpn-gnome`

`├── Import: .ovpn config files`

`└── Usage: Settings → Network → VPN → Import`
```

**2. WireGuard**

```
`├── Packages: network-manager-wireguard`

`├── Import: .conf files or manual configuration`

`└── Usage: Settings → Network → VPN → Import or Add`
```

**3. IPSec/L2TP**

```
`├── Packages: network-manager-l2tp, network-manager-strongswan`
```

## Captive Portal Detection

### Automatic Detection

Many public Wi-Fi networks (cafes, airports, hotels) require a web login before internet access is granted.

Spike detects and handles captive portals automatically:

Detection mechanism:

```
`├── NetworkManager checks connectivity on connection`

`├── HTTP request to http://connectivity-check.ubuntu.com/`

`│   (or spike-branded check URL: http://connectivity.spike.bigrangatech.com/)`

`├── If response is not expected: captive portal suspected`

`├── NetworkManager emits CaptivePortal signal`

`└── Spike Shell responds`
```

Response:

```
`├── Notification: "This network requires a login. Opening browser..."`

`├── Firefox opens to the captive portal page`

`├── User completes login in browser`

`├── NetworkManager re-checks connectivity`

`└── If successful: "Connected to \[network name\] with internet access"`
```

**Settings → Network → Advanced:**

```
`├── \[x\] Auto-detect captive portals (default: On)`

`├── \[x\] Auto-open browser for login (default: On)`

`└── If disabled: user must manually open Firefox to navigate to portal`
```

Known issues:

```
`├── Some captive portals block HTTP (force HTTPS redirect)`

`├── Some portals require a specific user-agent`

`├── If auto-detection fails: user can open Firefox manually`

`│   └── Almost all portals redirect to login page on any HTTP request`

`└── This is handled by the connectivity check (Golden Rule 2 compliant)`
```

## Airplane Mode

### Implementation

Airplane mode uses `rfkill` to disable all wireless radio:

Implementation:

```
`├── Toggle via tray applet or Settings`

`├── Command: rfkill block all (enable airplane mode)`

`├── Command: rfkill unblock all (disable airplane mode)`

`├── Persists across reboots (state saved to /var/lib/spike/airplane-mode)`

`└── On boot: spike-session reads saved state and applies rfkill`
```

What airplane mode blocks:

```
`├── Wi-Fi (all adapters)`

`├── Bluetooth (all adapters)`

`├── Mobile broadband (if present)`

`└── GPS (if present and controllable via rfkill)`
```

What it does **not** block:

```
`├── Ethernet (wired connection still works)`

`└── USB-connected peripherals`
```

Airplane mode toggle:

```
`├── Tray applet: airplane icon, click to toggle`

`├── Keyboard: Fn + Airplane key (if present on keyboard)`

`├── Settings → Network → Airplane Mode toggle`

`└── Launcher → search "airplane"`
```

Notification on toggle:

```
`├── On: "Airplane mode enabled. Wi-Fi and Bluetooth are now off."`

`└── Off: "Airplane mode disabled. Wi-Fi and Bluetooth are available."`
```
